# Trust Platform — Product & Engineering Roadmap

> Status date: 2026-11-07 · Owner: Trust Platform · Repository: `knehari/trust-platform`
> **This is a technical roadmap, not a release announcement.** Versions below label laboratory increments and proposed future milestones, not published production releases.

## Status conventions

- **LAB-VALIDATED**: code and relevant tests evidenced on an exact laboratory tree; the change may still be in a Draft PR and is not production approved.
- **LAB-PROTOTYPE**: scoped code/contract and tests available; full integration, CI and independent review may remain open.
- **PLANNED**: proposed scope, no implementation claim. Future version numbers are planning labels, subject to architecture review.
- **G0 EVIDENCE PENDING**: the owner confirmed legal/IP clearance and independent security review on 2026-11-07; the corresponding review artifacts have not been linked to this repository checkpoint.

## Current baseline and release hygiene

- **`main` is not a shipped CA.** The first integration phase brings the laboratory profile lifecycle, console, IAM and read API stack into the code baseline. Experimental revocation/CRL and signed administration from [Draft #94](https://github.com/knehari/trust-platform/pull/94) remain in an [incomplete integration branch](https://github.com/knehari/trust-platform/tree/codex/revocation-port-onto-profile). The version history below records **development milestones**, not GitHub releases.
- Technical test success is not production readiness; no eIDAS/ETSI/ANSSI qualification, no QTSP certification, no audited production HSM custody or network-facing production CA claimed.
- Integrate stacked work in dependency order, assess security and cryptographic algorithms, validate migrations and isolated CI, then merge through authorized review gates. The owner's G0 and independent-review confirmation does not substitute for linking the evidence to the release record.

## MVP: controlled single-tenant PKI pilot

The first viable version means an authorized operator can create a CA and a certificate profile, issue and revoke a certificate through authenticated application routes, inspect durable evidence, and recover the service and its protected keys in a controlled pilot. It is **not** a qualified trust service or a general-availability release.

**Progression: 5/12 criteria evidenced (42%)** · `█████░░░░░░░` · **MVP not reached**.

Each checkbox is one criterion, so the bar is `completed / 12`, rounded to the nearest whole percent. A checked foundation means implemented and tested **in the laboratory**, including code still in a Draft PR; it does not mean merged, independently reviewed or production-approved. An unchecked criterion may have partial prototypes, but its full MVP acceptance condition remains open.

- [x] **CA core and safe issuance foundations:** policy checks, issuer-scoped serial/idempotency, durable intent, independent signature verification and ambiguity-safe recovery in laboratory paths ([PRs #1–#9](https://github.com/knehari/trust-platform/pulls), [recovery status](docs/recovery/EXECUTION_STATUS.md)).
- [x] **Scoped read API:** OIDC-token and server-owned CA-grant checks, bounded reads, readiness and cursor pagination are exercised against disposable PostgreSQL ([Drafts #50–#70](https://github.com/knehari/trust-platform/pulls)). The test issuer is not human IAM.
- [x] **Read-only operator console:** CA/certificate/audit consultation, detail dialogs, search, export and recorded-date filters are exercised in the laboratory; profile-draft consultation is proposed through [Draft #140](https://github.com/knehari/trust-platform/pull/140). These views do not issue or revoke certificates.
- [x] **Reproducible laboratory stack and data checks:** disposable Compose/browser flow, restricted database role, migrations and logical restore regressions ([Drafts #53, #61–#69 and PR #129](https://github.com/knehari/trust-platform/pulls)). This is not operational disaster recovery.
- [x] **Human IAM and authorization (laboratory):** an isolated Keycloak realm authenticates distinct maker/checker accounts and a workload client; role, CA grant and negative-access checks run against signed tokens ([ADR-0009](docs/adr/ADR-0009-laboratory-identity-provider.md), Proposed). MFA, production transport and operational IdP controls remain open.
- [ ] **CA and profile lifecycle:** policy-controlled API and console workflows to create, approve, activate and retire CAs and versioned certificate profiles; no direct database bypass. The profile half is in the laboratory: recording and submitting drafts ([ADR-0010](docs/adr/ADR-0010-profile-draft-writes.md)), signed approval or rejection ([ADR-0011](docs/adr/ADR-0011-signed-profile-decisions.md)) and activation or retirement against declared CA capabilities ([ADR-0012](docs/adr/ADR-0012-profile-revision-activation.md)), all Proposed. The CA half has begun: a CA administrator proposes a CA and registers its verified self-signed issuer certificate ([ADR-0013](docs/adr/ADR-0013-ca-proposal-and-issuer-certificate.md), Proposed), two CA approvers sign its approval and an administrator activates it ([ADR-0014](docs/adr/ADR-0014-ca-approval-and-activation.md), Proposed); a single administrator suspends a CA at once, while its reactivation or retirement needs two signers again, and retirement retires its active profiles ([ADR-0015](docs/adr/ADR-0015-ca-suspension-and-retirement.md), Proposed). The criterion stays open until issuance uses these states.
- [ ] **Application issuance:** authenticated CSR submission and approval, profile enforcement, Core orchestration, idempotent API result and end-to-end negative/fault tests. First slice in the laboratory: verified CSR applications bound to the active profile of an ACTIVE CA, approved by a registration officer other than the requester ([ADR-0016](docs/adr/ADR-0016-certificate-applications.md), Proposed). Second slice: approved applications issued once through the core state machine and a separate laboratory signer with a software key, verified independently before storage ([ADR-0017](docs/adr/ADR-0017-application-issuance-lab-signer.md), Proposed). Third slice: registered RA systems obtain certificates with requests signed by their own P-256 key, under the profile's rules, issued once and verified independently ([ADR-0025](docs/adr/ADR-0025-ra-issuance-channel.md), Proposed). Fourth slice: the RA revokes, with a signed request, the certificates it obtained; the next CRL lists them ([ADR-0026](docs/adr/ADR-0026-ra-revocation-channel.md), Proposed). Open: RA key rotation, production transport and custody. Subscriber identity and domain-control validation belong to a light RA or the CLM, not to the CA ([ADR-0024](docs/adr/ADR-0024-ca-ra-responsibility-boundary.md), Proposed); reconciliation and revocation landed in later slices.
- [ ] **Revocation and publication:** authorized revocation with durable audit evidence and verifiable CRL publication; OCSP and broader path validation require a separate design decision. First slice in the laboratory: revocation requested by the requester or an officer and approved by a different registration officer, and on-demand v2 CRLs signed by the laboratory signer after a journaled intent, verified before storage and by OpenSSL ([ADR-0018](docs/adr/ADR-0018-revocation-and-crl.md), Proposed). Second slice: owner-configured CRL distribution points in issued certificates and an unauthenticated latest-CRL route that `openssl verify -crl_download` uses, with renewal status ([ADR-0019](docs/adr/ADR-0019-public-crl-publication.md), Proposed). Open: scheduled renewal, OCSP, reconciliation tooling, production custody.
- [ ] **Protected signing keys:** real HSM/PKCS#11 integration, key ceremony, custody and tested ambiguous-outcome reconciliation; software laboratory keys do not meet this criterion.
- [ ] **Durable audit evidence:** persisted authenticated event chain, integrity/tamper checks, exportable verification manifest and governed retention. First slice in the laboratory: committed audit events are sealed after commit into a persisted SHA-256 hash chain, which an independent Rust tool recomputes and checks against a head exported earlier, printing a JSON manifest ([ADR-0022](docs/adr/ADR-0022-tamper-evident-audit-chain.md), Proposed). Second slice: the laboratory signer signs checkpoints of the chain with a separate audit key, only after recomputing every link since the last checkpoint it remembers outside the database, so a rewritten or rolled-back database is refused and fails verification ([ADR-0023](docs/adr/ADR-0023-signed-audit-checkpoints.md), Proposed). Open: hardware-protected audit key, authenticated actor claims, external log, governed retention.
- [ ] **Operational recovery:** protected database and key backup/restore, migration rollback, incident runbooks and measured pilot RTO/RPO.
- [ ] **Release gates:** G0 legal/IP clearance, independent PKI/security review, final-commit CI and an explicitly approved controlled-pilot release decision.

- [x] Approve a key-attested CA proposal with two distinct CA approvers who sign the exact claim the database builds with their own owner-registered P-256 keys (never also profile approver keys), then activate it (migration 0027, [ADR-0014](docs/adr/ADR-0014-ca-approval-and-activation.md) **Proposed**): an administrator who did not decide names the certificate digest; activation creates the CA with its attested suite as its only capability, after the API verifies the stored certificate again; an independent audit tool re-verifies certificates, decisions and activations. Software keys only; an activated CA cannot issue yet.
- [x] Suspend an activated CA at once (one administrator), and reactivate or retire it only through a change request approved by two CA approvers who sign the exact claim and applied by an administrator who did not decide (migration 0028, [ADR-0015](docs/adr/ADR-0015-ca-suspension-and-retirement.md) **Proposed**). No profile revision is activated for a CA that is not ACTIVE; retiring a CA retires its active profile revisions in the same transaction; the audit tool re-checks change decisions and applied changes. No revocation or publication, and no issuance path reads the state yet.
- [x] Submit certificate applications (migration 0029, [ADR-0016](docs/adr/ADR-0016-certificate-applications.md) **Proposed**): a requester with a per-CA grant sends a PKCS#10 CSR the API verifies (DER, P-256, proof of possession, exact CN), bound by the database to the active profile revision of an ACTIVE lifecycle-managed CA, with names inside its zones and validity within it; a registration officer other than the requester approves the exact application while the CA and revision are still active. CSR extensions are never used, domain control is not validated, and nothing is signed.
- [x] Issue approved applications in the laboratory (migration 0030, [ADR-0017](docs/adr/ADR-0017-application-issuance-lab-signer.md) **Proposed**): a registration officer, or the application's own requester, asks the API; the database creates the core request, reserves an issuer-scoped serial and journals the signing intent with the TBS digest before signing; a separate `trust-lab-signer` process on a Unix socket, the only one reading the CA's software key, re-checks the application, CA, revision, CSR, key and TBS itself and claims the intent once in the database before signing; the API verifies the certificate independently before storing it, and an ambiguous outcome becomes RECONCILIATION_REQUIRED, never a second signature. `lab_verify_issued_certificates` re-verifies every issued certificate. Laboratory key only, no HSM, no revocation.
- [x] Revoke issued certificates and publish signed CRLs in the laboratory (migration 0031, [ADR-0018](docs/adr/ADR-0018-revocation-and-crl.md) **Proposed**): the requester or a registration officer asks with an RFC 5280 reason from a closed list, and a different officer approves, which writes the immutable core revocation; an officer publishes a v2 CRL whose number never repeats and whose entries are fixed at the start, with the TBS digest journaled before the separate signer rebuilds the CRL from the database, claims it once and signs; the API verifies it before storage, readers fetch the DER, and OpenSSL verifies the CRL and reports the certificate revoked. The SQL test helper now fails on success when P0001 is expected, so the earlier immutability checks really run. No distribution point, OCSP or scheduled renewal.
- [x] Publish CRLs publicly in the laboratory (migration 0032, [ADR-0019](docs/adr/ADR-0019-public-crl-publication.md) **Proposed**): the database owner records one validated http(s) base URL per CA; new certificates carry exactly that cRLDistributionPoints URI, snapshotted with the signing intent so the signer and the audit tool check the same one; the API serves the latest published CRL there without authentication, through a view limited to publishing CAs; readers see whether renewal is due or the CRL expired, and the console alerts. `openssl verify -crl_check -crl_download` fetches the CRL by itself and reports the certificate revoked. Renewal stays manual.
- [x] Reconcile an ambiguous application issuance by voiding its serial under dual control (migration 0034, [ADR-0020](docs/adr/ADR-0020-issuance-reconciliation-void.md) **Proposed**): a registration officer proposes, recording whether the signer had claimed the intent; a different officer confirms under the CA's CRL lock; neither may be the requester. The application becomes VOIDED, the serial is never reused or re-signed, and every later CRL lists it without reason code, whether or not a certificate was produced. Recovering a signed-but-unstored certificate remains open.
- [x] Renew CRLs automatically in the laboratory (migration 0035, [ADR-0021](docs/adr/ADR-0021-automatic-crl-renewal.md) **Proposed**): a per-CA `crl-publisher` grant held by a system principal lets the API's renewal task publish a CRL only when it is due (none yet, or nextUpdate within two days), through the unchanged journaled path; officers still publish at any time; the status route and console show whether renewal is automatic. No OCSP, no alert channel beyond logs and the console.
- [x] Seal audit events into a tamper-evident chain in the laboratory (migration 0036, [ADR-0022](docs/adr/ADR-0022-tamper-evident-audit-chain.md) **Proposed**): after commit, the API's sealing pass links each event, oldest first, into an append-only SHA-256 chain over a canonical encoding of every column; readers see only whether an event is sealed; `lab_verify_audit_chain` recomputes every link in Rust from the raw rows and checks a previously exported head, so an owner who alters, removes or rebuilds history is detected against that head (not without it). No signed head, external store or retention policy.
- [x] Sign checkpoints of the audit chain in the laboratory (migration 0037, [ADR-0023](docs/adr/ADR-0023-signed-audit-checkpoints.md) **Proposed**): the lab signer holds a P-256 audit key distinct from the CA key and a state file outside the database; on the API's periodic request it recomputes the links since its last checkpoint from the raw events, refuses a database that no longer extends what it signed (`AuditRollback`, logged as an alert), signs the new head and records it in an append-only table; `lab_verify_audit_chain` verifies every checkpoint against the recomputed chain and the out-of-band public key. A restored database together with the signer's state is not detected; no HSM, external log or retention.
- [x] Accept signed issuance requests from registered RA systems in the laboratory (migration 0038, [ADR-0025](docs/adr/ADR-0025-ra-issuance-channel.md) **Proposed**): the database owner registers an RA's P-256 public key and grants it profiles per CA; `POST /v1/ra/cas/{ca_id}/certificates` takes no user token, verifies a fresh signature over the request (CA, profile, request id, CSR digest, names, validity), records the application as submitted and approved by the RA under the profile's rules with the signed bytes, and issues once through the signer; replays return the same certificate; the audit tool re-verifies every RA signature. No revocation through the channel, no key rotation, no TLS in the lab.
- [x] Revoke through the RA channel in the laboratory (migration 0039, [ADR-0026](docs/adr/ADR-0026-ra-revocation-channel.md) **Proposed**): a registered RA revokes only certificates it obtained through the channel, with a fresh signed request (serial, reason code from the closed list, reason) that is both the request and its approval; the core revocation is written under the CRL lock and appears on the next CRL; the audit tool accepts the RA as both requester and approver only when its stored signature verifies. No on-revocation CRL publication or OCSP.
- [x] Publish a CRL as soon as a revocation is recorded, per CA, in the laboratory (migration 0040, [ADR-0027](docs/adr/ADR-0027-crl-publish-on-revocation.md) **Proposed**): an owner-set `publish_on_revocation` makes a CRL due when a revocation or void is not yet on the latest published CRL; the API requests a renewal pass right after each revocation, RA revocation or void, and the renewer publishes through the unchanged journaled path; the status route and console report the setting and the pending entries. Off by default; needs the renewer's grant; no OCSP or delta CRLs.
- [x] Make the signer verify a signed authorization before signing a certificate (migration 0041, [ADR-0028](docs/adr/ADR-0028-signer-verified-authorization.md) **Proposed**): registration officers sign their decisions with owner-registered P-256 keys over a claim the database builds from the application's exact facts; RA requests gain a version 2 that also signs a subject the RA chose among its validated names and optional extensions from a closed catalogue (`client-auth`, allowed per CA and profile by the owner); the signer rebuilds and verifies the RA's or the officer's signature before claiming, checks CSRs for proof of possession only, and refuses without a proof; the API refuses issuance without a proof before reserving a serial; the audit tool re-verifies officer claims and v2 requests; the console shows the claim and records the pasted signature. Incompatible change: unsigned application decisions are refused.
- [x] Make the signer verify a signed proof for every CRL entry (migration 0042, [ADR-0029](docs/adr/ADR-0029-signed-crl-entry-proofs.md) **Proposed**): an officer's revocation approval and the confirming officer's void become signed claims; before it claims a CRL intent, the signer checks that every entry recorded since the requirement is backed by an RA's signed revocation or an officer's signed claim with a key active when it signed, and refuses otherwise (the intent goes to reconciliation); earlier entries stay listed as legacy; the audit tool re-verifies every proof; the console signs revocations and voids like approvals. Incompatible change: unsigned revocation decisions and void confirmations are refused. Void proposals stay unsigned.
- [x] Publish CRLs through a separate publisher and static server in the laboratory (migration 0043, [ADR-0030](docs/adr/ADR-0030-separate-crl-publication.md) **Proposed**): the management API serves nothing anonymous any more; `trust-crl-publisher`, with a login limited to one feed view, verifies each latest CRL under the issuer certificate, refuses older numbers than the one already served, and writes the static tree atomically; a plain nginx with no database access serves it at the unchanged distribution point path on its own port. Plain HTTP on loopback; no CDN.
- [ ] Sign approved applications with a separate laboratory signer that alone reads the CA key, through the core's journaled intent, independent verification and recovery, refusing suspended or retired CAs (criterion 7).
- [ ] Expose policy-controlled issuance through the Rust Core, with a real identity boundary before pilot use.
- [ ] Add revocation, publication and durable evidence paths, then complete custody/recovery and independent release gates.
