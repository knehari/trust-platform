# Management console (laboratory)

React/TypeScript console for the read-only [management API](../docs/architecture/management-api-readonly.md). The UI calls the real `/v1` endpoints through Vite's local proxy; it contains no CA fixtures or mocked API responses. API failures show a validated `X-Request-Id` when supplied, so operators can correlate an error with the service log. It shows scoped CA inventory, CA details, certificate metadata and audit metadata with independent loading, error, retry and empty states for certificate and audit lists. Retrying one list does not refetch the other. A response containing a row from another CA is rejected; previously loaded rows are hidden immediately when the selected CA changes. Authority, certificate and audit filters search only records already loaded in their respective lists; loading older pages expands that set. Exact certificate request UUID or issuer-scoped serial lookups and audit event UUID lookups find records beyond loaded pages and open the same metadata modals. Authority, request and audit UUID inputs accept plain, braced and `urn:uuid:` forms; the client sends only the canonical UUID and checks the returned record. Serial lookup accepts hexadecimal digits, an optional `0x` prefix, or colon-separated bytes (for example `0x10001` or `01:00:01`); it normalizes to canonical positive DER-content hex before the exact lookup. Decimal notation is not supported. The CA list loads at most 100 rows at a time with a "Load more authorities" action; an exact authority UUID lookup can select an authorized CA outside loaded pages without changing the loaded-row count, and remains available when inventory loading fails. A full inventory refresh clears previously displayed CA and history rows before revalidation, so a failed refresh cannot leave stale records on screen. Certificate and audit lists also load at most 100 rows at a time; a "Load older" action follows the server's CA-scoped cursor until no more rows remain. Selecting a certificate serial opens its already loaded, CA-scoped metadata in a modal; no second API request is needed, and the console never downloads certificate DER. Selecting an audit event opens its already loaded, CA-scoped metadata in a modal without exposing the actor identifier. The modals can copy exact technical IDs and certificate fingerprint values to the local clipboard. They can also copy a JSON object built from an explicit allowlist of certificate or audit metadata fields; certificate DER, private keys, actor identity and raw evidence are not included. Certificate detail shows the recorded subject CN; the Rust lab journal derives it from a verified, plain single-CN X.509 subject. Historical rows without CN metadata say “Not recorded”. Disposable SQL fixtures use explicitly synthetic `*.lab.invalid` display names because their DER sentinel is not a certificate.

The certificate inventory shows recorded CNs directly and includes them in its loaded-row filter. That filter also recognizes the serial formats accepted by exact lookup, but only searches rows already loaded in the browser. The certificate list can be locally sorted by signed time, CN or serial without changing the server pagination cursor or fetching additional rows. The same loaded-row-only sorting is available for audit events by recorded time, type or decision. The browser URL records the selected section and CA ID (for example `/?view=certificates&ca=<uuid>`), including across the laboratory OIDC redirect. On opening a link, the server must still authorize the CA through the normal signed scope and database grant; no access token appears in the URL. A missing CN appears as a dash in the table and “Not recorded” in detail; neither view derives a CN from a serial or fingerprint. `npm ci && npm run build` typechecks and builds the app. For local development, copy `.env.example` to `.env.local`, start the API, run `npm run check-api`, then run `npm run dev`. The API check sends unauthenticated requests to the authority, profile-draft list, certificate request/serial and audit detail routes and expects 401; a 404 indicates an older backend binary that needs rebuilding and restarting. Use an OIDC public client with Authorization Code + PKCE and callback `http://127.0.0.1:5173/auth/callback`. The backend must accept access tokens from that issuer and the audience `trust-api`. Session data is stored by `oidc-client-ts` in browser session storage; the UI never handles CA keys. A production deployment requires a same-origin reverse proxy for `/v1`, a real IAM service, TLS and security review.

The page heading offers “Copy view link” after scoped authorities finish loading. It copies only the current section and selected CA UUID on the console's own origin, and shows a visible success or failure message. Opening the link in another session still requires sign-in and a server-owned grant for that CA.

## Disposable browser-to-database smoke test

This repository includes `npm run test-issuer`, a **loopback-only OIDC fixture**. It auto-approves a single ephemeral `lab-operator` and signs access tokens with a freshly generated key. It performs no human authentication and must never be used for deployment or real users. It intentionally binds only `127.0.0.1:8080` and puts only the fixed laboratory CA UUID `eeeeeeee-eeee-4eee-8eee-eeeeeeeeeeee` in the signed scope. The API also requires a separate server-owned database grant for that CA.

In a disposable PostgreSQL 16 database, apply migrations `0001`–`0016`, insert that CA and another CA, and as database owner insert `management_reader_grant('http://127.0.0.1:8080','lab-operator','eeeeeeee-eeee-4eee-8eee-eeeeeeeeeeee')`. Create a separate login with `trust_api_reader` and verify `tests/management_api_readonly.sql`. The [Compose runbook](../docs/development/lab-compose.md) automates this disposable seed. Then start three processes in this order:

1. `cd frontend && npm ci && npm run test-issuer`
2. From the repository root, set `TRUST_DATABASE_URL` to the restricted login, `TRUST_OIDC_ISSUER=http://127.0.0.1:8080`, `TRUST_OIDC_AUDIENCE=trust-api`, then run `cargo run -p trust-management-api --locked`.
3. `cd frontend`, set `VITE_OIDC_ISSUER=http://127.0.0.1:8080` and `VITE_OIDC_CLIENT_ID=trust-console`, then run `npm run dev`.

Open `http://127.0.0.1:5173`, sign in, and verify that only the allowed CA appears. The Compose seed includes one synthetic certificate metadata record and one synthetic audit event for that CA; a manually seeded database may show empty views. These records do not establish real issuance. Fresh Compose and pagination fixtures include synthetic CN metadata. To refresh an existing disposable 102-row pagination fixture after migration 0014 without recreating it, run `psql '<disposable-pagination-database-url>' -X -v ON_ERROR_STOP=1 -f scripts/lab/restore-pagination-fixture-cn.sql` from the repository root; the script refuses non-fixture rows. It must never be run against real certificate data. The test issuer's key changes on restart; the API refreshes its JWKS when it sees the new key ID, subject to a five-second retry bound. Previously cached keys expire from the verifier within 60 seconds. Do not copy this fixture into production Compose.

Browser smoke evidence on 2026-10-17: Authorization Code + PKCE exchanged once; dashboard displayed the single authorized `Allowed CA` from a populated two-CA PostgreSQL database; detail, certificate empty state, audit empty state, logout and fresh login were exercised. This does not prove production IAM or an HTTP issuance path.

The console can restore a scoped view and a certificate/audit detail from a URL after the API rechecks access. Browser Back/Forward restores the view and authority. Certificate CN prefix and audit date/type forms query the entire selected authority history through the API, with the same 100-row cursor pages; local text filters and sorts still affect only loaded rows. An older API binary may ignore the new query parameters, so refresh the local API before relying on these filters.

A separate authority search calls the API across the full signed-and-granted CA scope by name or policy prefix. The existing authority filter continues to act only on currently loaded rows.

Newest/oldest choices request the API's complete-history order and reset pagination. CN, serial, event type and decision choices still sort only the rows already loaded and are labeled as such.

## Profile proposals

The Profile proposals view reads only immutable DRAFT revisions for the selected, authorized CA. It follows the API cursor in pages of at most 100 and rejects rows belonging to another CA. An exact revision detail opens in a modal and shows advisory syntax warnings and the deterministic content digest. A direct link such as `/?view=profiles&ca=<uuid>&profile=server-lab&revision=2` rechecks the exact revision and CA grant after sign-in, including when the revision is outside the loaded page. Two loaded revisions of the same profile can be compared locally; the comparison cannot access another CA or approve either revision. The Compose seed includes two visible revisions and one hidden-CA proposal for isolation checks. These records have no approval, activation or issuance effect; there is no profile editing or CA-creation action in the browser.
