# Threat model — v0.1

## Assets
CA private keys, issuance policy, authenticated identities, certificate/serial database, CRL, audit chain, signing authorization.

## Trust boundaries
User/API -> authenticated control plane -> policy engine -> CA signing service -> signing provider/HSM; persistence and publication are separate boundaries.

## Threats and controls
- Unauthorized issuance: requester binding, least privilege, policy approval, negative tests.
- CSR parser abuse: size limits, fuzzing, strict DER and X.509 validation.
- Key theft: HSM/PKCS#11 isolation, no key export by default, no secret logging.
- Serial duplication: unique issuer+serial constraint, durable reservation.
- Signature ambiguity: reconciliation and no blind retry.
- CRL manipulation/staleness: signed CRLs, controlled publication, freshness monitoring.
- Supply chain: pinned dependencies, SBOM, SCA, provenance, signed releases.
- Insider abuse: role separation, privileged action audit, two-person control where justified.
- Cross-authority reads through the management API: the token's CA scope intersected with server-owned grants in every API query, and since migration 0021 the same restriction inside every management view for the principal the API declares; a session that declares none reads nothing. The database cannot authenticate the declared principal, so a compromised API process or a holder of the reader login can still read any granted principal's authorities ([ADR-0008](../adr/ADR-0008-database-reader-isolation.md), Proposed).
- Impersonation and token confusion at the management API (laboratory, [ADR-0009](../adr/ADR-0009-laboratory-identity-provider.md), Proposed): people sign in through a Keycloak realm with per-user passwords and lockout after repeated failures; the API accepts only RS256 `at+jwt` access tokens of the pinned issuer and audience that were issued to the console client (`azp`), so workload, ID and foreign-realm tokens are refused; roles grant only their own permission. Open: no multi-factor authentication, development-mode Keycloak, workload identity by shared secret, and anyone administering the realm can mint users, roles and CA scopes (database grants remain a second, owner-held layer).
- Unauthorized or forged profile changes (laboratory, [ADR-0010](../adr/ADR-0010-profile-draft-writes.md), Proposed): writes need the editor token role, the CA in scope and an owner-held role grant; they go through a login limited to two `SECURITY DEFINER` functions that recompute the revision digest, serialize per profile, refuse stale or already submitted revisions and record lifecycle and audit events atomically; idempotency keys make retries safe and refuse key reuse. Open: the database trusts the principal the API declares (a compromised API or writer login can act as any granted editor), denied attempts are not persisted as audit events, and no approval or activation exists yet.
- Forged or self-approved profile decisions (laboratory, [ADR-0011](../adr/ADR-0011-signed-profile-decisions.md), Proposed): two approvers with owner-held grants and distinct owner-registered P-256 keys must each sign the claim the database builds for the exact submission; the API verifies each signature before commit, the author and submitter cannot decide, and `lab_verify_profile_decisions` re-verifies every stored decision. Open: PostgreSQL does not verify ECDSA (a compromised API or writer login can record an unsigned decision until the audit tool runs), keys are software files without custody, registration proves no possession, and there is no MFA.
- Activation of an unapproved or incompatible profile (laboratory, [ADR-0012](../adr/ADR-0012-profile-revision-activation.md), Proposed): only an independent CA operator with an owner-held grant activates an APPROVED revision by its exact digest; the CA's policy version and owner-declared, catalogue-checked suites must match; the pointer key keeps one active revision per profile. Open: declared capabilities are not provider evidence, the issuer certificate is not checked, one operator suffices, and no issuance path uses the active revision yet.
- A forged or mismatched CA issuer certificate, or a CA key reused across CAs (laboratory, [ADR-0013](../adr/ADR-0013-ca-proposal-and-issuer-certificate.md), Proposed): only an owner-granted CA administrator proposes; the API accepts only a currently valid, self-signed P-256 root that verifies under its own key, with critical CA constraints and key usage; the database binds it to the proposal's name and suite, once, and refuses a public key already registered. The private key never reaches the platform. Open: one administrator suffices, the key is a software file without custody evidence, the database trusts the API's X.509 parsing, and no audit tool re-verifies stored certificates yet.
- Unilateral or forged CA activation (laboratory, [ADR-0014](../adr/ADR-0014-ca-approval-and-activation.md), Proposed): two distinct owner-granted CA approvers, neither the proposer nor the registrant, sign the exact claim binding the certificate and key with distinct registered keys that can never also approve profiles; an administrator who did not decide activates by digest; the API re-verifies the stored certificate before the CA exists; `lab_verify_ca_lifecycle` re-checks certificates, decisions and activations, which closes the ADR-0013 gap. Open: software keys without custody or MFA, and the audit tool runs only in CI.
- Unilateral resumption or retirement of a CA (laboratory, [ADR-0015](../adr/ADR-0015-ca-suspension-and-retirement.md), Proposed): one administrator can only suspend; reactivation and retirement need a request, two signed approvals by CA approvers other than the requester, and application by an administrator who did not decide, in the state the request was made in; a suspended or retired CA cannot gain active profiles, and retirement retires its active ones. Open: a single administrator can suspend (denial of service, accepted and audited), retirement revokes and publishes nothing, and no issuance path reads the state yet.
- Unauthorised or out-of-policy certificate requests (laboratory, [ADR-0016](../adr/ADR-0016-certificate-applications.md), Proposed): only a granted requester submits; the API verifies the CSR's proof of possession and exact CN and never uses its extensions; the database binds the application to the active profile revision of an ACTIVE CA and checks names, zones (label boundary), count, validity and that the key is not the CA's; a different, granted registration officer approves while the CA and revision are still active. Open: no domain-control validation, the officer's decision is not signed, the database trusts the API's CSR parsing, and nothing is signed yet.
- Certificates for names the subscriber does not control (boundary, [ADR-0024](../adr/ADR-0024-ca-ra-responsibility-boundary.md), Proposed): identity proofing and domain-control validation are the light RA's or the CLM's (ACME) responsibility, not the CA's. The CA trusts the authorized RA decision and still enforces the active profile's zones, key policy, validity and fixed extensions, so a compromised or careless RA is bounded to the profile's zones, not stopped within them. Every issuance and revocation must stay attributable to an authenticated RA actor.
- Forged or replayed RA requests (laboratory, [ADR-0025](../adr/ADR-0025-ra-issuance-channel.md), Proposed): only RA systems the database owner registered, with profiles granted per CA, can request; every request is signed with the RA's P-256 key over its exact content and must be within 300 seconds; one request identifier binds one set of signed bytes; the bytes and signature are stored and re-verified by the audit tool. A stolen RA key yields certificates within that RA's profiles and zones until the owner disables it; the API, not PostgreSQL, verifies the signature at request time.
- Unauthorised RA revocation (laboratory, [ADR-0026](../adr/ADR-0026-ra-revocation-channel.md), Proposed): an RA revokes only certificates it obtained through the channel, with a fresh request signed by its registered key, under the closed list of reason codes and the CRL lock; the audit tool accepts an RA as both requester and approver only when its stored signature verifies. A stolen RA key can revoke that RA's certificates (denial of service within its scope) until the owner disables it.
- Unauthorised, duplicated or altered signing (laboratory, [ADR-0017](../adr/ADR-0017-application-issuance-lab-signer.md), Proposed): only an officer or the application's own requester starts issuance of an APPROVED application of an ACTIVE CA and active revision; the signing intent and TBS digest are journaled before signing; a separate signer with a read-and-claim-only login re-verifies the CSR, its key against the CA's attested key and the TBS against the application, and the database accepts one claim per intent, so a compromised API cannot get an intent signed twice or a different TBS signed; the API verifies the certificate before storage and an audit tool re-verifies stored certificates. Open: the CA key is a software file on the laboratory host read by a root container, no reconciliation tooling for applications, no revocation, no rate limit, no domain-control validation.
- Unauthorised, forged or silent revocation, and stale or rolled-back CRLs (laboratory, [ADR-0018](../adr/ADR-0018-revocation-and-crl.md), Proposed): only the requester or an officer asks, with a reason from a closed list, and a different granted officer approves; core revocations are immutable; CRL numbers are allocated by the database and never reused, only the latest intent can be signed, its entries are fixed under the CA's CRL lock and its digest is journaled before the signer rebuilds and claims it once; the API verifies the CRL before storage and the audit tool re-verifies every revocation and CRL. Open: CRLs are fetched only through authenticated readers (no distribution point), renewal is manual before nextUpdate, no OCSP, revocation decisions are not signed.
- Misdirected or unavailable CRL distribution (laboratory, [ADR-0019](../adr/ADR-0019-public-crl-publication.md), Proposed): only the database owner records a CA's base URL, once, validated (http(s), no credentials, path or query); certificates carry exactly the URL snapshotted with their signing intent, which the signer and the audit tool check; the unauthenticated route serves only the latest published CRL of publishing CAs through a dedicated view. Open: no rate limit or cache on the public route, plain HTTP in the laboratory (CRLs are signed, availability is not protected), manual renewal with only status alerts.
- Forged approvals accepted by the signer (laboratory, [ADR-0028](../adr/ADR-0028-signer-verified-authorization.md), Proposed): the signer no longer trusts the APPROVED state the API writes. For every intent it rebuilds and verifies either the RA's signed request (v1, or v2 binding the subject and optional extensions) or a registration officer's signed approval over the application's exact facts, with a key only the database owner registers (enabled RA, active officer key); otherwise it refuses before any claim. The subject comes from the authorization, the CSR proves possession only, and optional extensions come from a closed catalogue the owner allows per profile. A compromised API or writer login can record unsigned approvals but cannot get them signed; the API refuses such issuance before reserving a serial. Open: a compromised owner login can register keys; officer and RA keys are software files without custody or MFA.
- Forged revocations listed by the CA (laboratory, [ADR-0029](../adr/ADR-0029-signed-crl-entry-proofs.md), Proposed): every CRL entry recorded since migration 0042 needs an RA's signed revocation or an officer's signed revocation approval or void confirmation, with a key the owner registered and that was active when it signed; the signer rebuilds and verifies each before it claims the CRL intent, and never drops a listed entry. A compromised API can still record an unsigned revocation, which blocks every later CRL of that CA (visible: reconciliation, console, audit tool) until the owner intervenes: integrity over availability. Open: void proposals are not signed; the owner login can register keys.
- Anonymous load or defects on the CRL distribution path reaching the management plane (laboratory, [ADR-0030](../adr/ADR-0030-separate-crl-publication.md), Proposed): the API no longer serves anything without authentication; a separate publisher with a login limited to one view verifies each CRL under the issuer certificate and never replaces a newer public CRL with an older one; a static server without database access serves the files. Open: plain HTTP, no caching/CDN, the publisher container runs as root to write its volume.
