# Threat model — v0.1

## Assets
CA private keys, issuance policy, authenticated identities, certificate/serial database, CRL, audit chain, signing authorization.

## Trust boundaries
User/API -> authenticated control plane -> policy engine -> CA signing service -> signing provider/HSM; persistence and publication are separate boundaries.

## Threats and controls
- Unauthorized issuance: requester binding, least privilege, policy approval, negative tests.
- CSR parser abuse: size limits, fuzzing, strict DER and X.509 validation.
- Key theft: HSM/PKCS#11 isolation, no key export by default, no secret logging.
- Serial duplication: unique issuer+serial constraint, durable reservation.
- Signature ambiguity: reconciliation and no blind retry.
- CRL manipulation/staleness: signed CRLs, controlled publication, freshness monitoring.
- Supply chain: pinned dependencies, SBOM, SCA, provenance, signed releases.
- Insider abuse: role separation, privileged action audit, two-person control where justified.

## Revocation and CRL write path (lab, migrations 0014-0032, ADR-0006, ADR-0007)

| Threat | Control in the lab slice | Residual risk / open |
| --- | --- | --- |
| A service login revokes, releases or suspends without maker-checker by writing tables directly | 0023: tables owned by NOLOGIN `trust_revocation_owner`; SECURITY DEFINER functions; capability roles have EXECUTE only (tests/revocation_privileges.sql) | Superusers, the owner role and anyone able to `SET ROLE` to it bypass; deployment must keep service logins out of those |
| An issuance service login stores a certificate that never had a signing intent, rewrites an intent or skips the policy gate | 0035: the issuance functions are SECURITY DEFINER owned by NOLOGIN `trust_issuance_owner` (table rights limited to what the functions and gate triggers need; `ca` only `policy_gate_epoch`); `trust_issuance_service` has EXECUTE only, no table access (tests/revocation_privileges.sql, `issuance_service_role_issues_through_functions_only`) | Policy administration (gate activation, draft approval, presign grants, dual-signature receipts), reconciliation review and collector evidence still run with the migration login's rights; `PgIssuanceStore::connect_lab_service` / `from_service_client` refuse a superuser, CREATEROLE, BYPASSRLS or owner-member login, but only for services that use them; superusers and the owner bypass |
| One actor plays maker and checker by asserting two identities | Database refuses equal `(issuer, subject)`; officer grants are server-owned | Identities are asserted by the calling service: textual, not key-distinct (known deviation from AGENTS.md). ADR-0007 steps 1-2 (0028-0029): enrolled P-256 keys and persons under CA-admin dual control; per CA, `signed_approvals_required` makes maker and checker sign the canonical claim with WebAuthn (UP+UV, origin, counter, single-use challenge), with distinct keys and persons. Open: the database cannot verify ECDSA, so a holder of the officer API role could store a forged assertion (exposed by `reverify_signed_change`); since 0039 rejections and withdrawals are signed too on such CAs (a forged rejection used to drop a revocation silently); CA-admin actions are signed only where `signed_admin_required` is set (0037); IAM person ids are asserted |
| Fake coverage: rows added to a CRL snapshot or a `STORED` row inserted without signing | No INSERT for services (0023); snapshot and publication guards; store checks digests | Owner/superuser can still insert |
| CRL signed by another CA's key or stored under the wrong CA | 0022 registered issuer certificate per CA; `crl_once` checks the verifier issuer and the signer's SPKI before the intent | Key rollover not modelled; registration needs two CA admins (0024), signed with distinct keys and persons where `signed_admin_required` is set (0037), textual otherwise; DBA bootstrap outside dual control |
| Shadowing through `search_path` or temporary objects | Service functions pin `search_path = pg_catalog, public, pg_temp` (planted temp table test) | Independent review of every SECURITY DEFINER body (dynamic SQL, error leakage) still required |
| A service runs with a superuser or owner-member login and bypasses everything | `connect_lab_service` refuses privileged `session_user` (0024 commit) | Only enforced by the services that use it; deployment evidence required (ADR-0006 acceptance condition 2) |
| A single officer abuses or is tricked into a precautionary hold (ADR-0007 §6) | 0036: opt-in per CA, only under a CPS suspension reference; the officer signs a distinct `PRECAUTIONARY_SUSPEND` claim with an enrolled WebAuthn credential (single-use challenge); only a valid certificate; reversible hold only; fixed deadline, overdue holds alert in housekeeping; audit event and log line per use | 0038 caps open holds per officer and CA (`precautionary_hold_limit`, default 3), but several officers or several CAs still add up (availability, not integrity); the deadline does not lift a hold (fail closed); break-glass not implemented |
| One CA admin registers an issuer or grants officers alone, or grants themselves officer rights | 0024 `ca_admin_change`: two distinct admins, approval of the exact content digest, no self-grant. 0037 (opt-in, one-way per CA): both admins sign the `trust-platform/ca-admin/v1` claim with enrolled WebAuthn keys, distinct keys and persons; unsigned paths refused; an officer key or person can never be an admin's; evidence re-verifies offline (`reverify_admin_change`) | Admin keys are bootstrapped by the DBA until `signed_admin_required` is set; after that they change only by signed dual control (0040), and losing keys has no recovery path yet (break-glass open). DBA removal stays open (it only takes signing power away); the database cannot verify ECDSA, so a holder of `trust_ca_admin` could store a forged assertion (exposed by re-verification); textual where the setting is off; rejection is unsigned |
| Stale or superseded CRL signed late, or a CRL misdated by a wrong database clock | Only the highest reserved number may record an intent; staleness and nextUpdate checks (0017, 0020, 0021); the Rust core refuses a reservation whose thisUpdate disagrees with its clock beyond 2 s and housekeeping alerts on skew (ADR-0006 G) | Both clocks wrong together is not detected; authenticated time (NTS) is a deployment requirement |
| A function, grant or guard is changed outside a reviewed migration (e.g. `SECURITY DEFINER` reset, trigger disabled) | Catalog invariant in tests/revocation_privileges.sql (0025); 0026 event triggers record every DDL and object grant (append-only, `ENABLE ALWAYS`, no SQL text) and `crl_housekeeping` alerts on changes no reviewed migration acknowledged | Roles, role membership, `ALTER SYSTEM` and event triggers themselves are not recorded (server logging/pgaudit needed); a superuser can drop the triggers or the rows (external anchoring, ADR-0006 condition 5) |
| A superuser rewrites, deletes or truncates the audit trail, or recomputes it consistently | 0027 sealed hash chain over `audit_event` and `schema_change_audit`; Rust re-encodes every record and checks heads against checkpoints exported outside the database (`audit_chain_anchor`, exit 3) | Unsealed records and entries after the last checkpoint; checkpoints signed with a lab key file (HSM custody open) but not third-party timestamped; forged records inserted before sealing are sealed too |
| A CRL altered or substituted in the database is published to relying parties; the public endpoint becomes a write path | 0030: `trust_crl_publisher` can only read the latest stored CRL; the distribution point refuses privileged logins and re-verifies signature, issuer, number and times before serving (503 otherwise) | No HTTP TLS or availability engineering (the database link uses verified TLS 1.3); a stale CRL is still served (uncached); denial of service by withholding new CRLs is not detected here (housekeeping `crl_due`) |
| A revoked certificate silently disappears from CRLs through pruning | 0031: pruning is opt-in, refused for ETSI EN 319 411-2, only after a stored CRL issued past `not_after` listed the entry; `not_after` comes from the verified certificate at issuance and is immutable; NULL is never pruned | Since 0032 the Rust core re-reads every omitted entry's stored certificate before signing and refuses an expiry the DER does not confirm. Residual: a superuser can replace the stored DER and `not_after` together (since 0035 the issuance service login cannot) |
| An HTTP caller acts as another officer, or a service answers a challenge on an officer's behalf | Revocation write API (lab): actor = verified token `(iss, sub)`, role and CA scope required, unknown fields refused, challenge bound to its officer, assertion verified in Rust before writing, officer-API login only | No HTTP TLS termination, rate limiting or session binding beyond the token (database connections use verified TLS 1.3 since iteration 19); a holder of the officer API database role can still bypass the API (ADR-0007 §7) |
| Lost or ambiguous signature | Durable intent before signing, quarantine, reconciliation of a held DER (0021), housekeeping alerts | A CRL lost with its process cannot be recovered (no signer read-back) |
