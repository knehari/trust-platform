# Threat model — v0.1

## Assets
CA private keys, issuance policy, authenticated identities, certificate/serial database, CRL, audit chain, signing authorization.

## Trust boundaries
User/API -> authenticated control plane -> policy engine -> CA signing service -> signing provider/HSM; persistence and publication are separate boundaries.

## Threats and controls
- Unauthorized issuance: requester binding, least privilege, policy approval, negative tests.
- CSR parser abuse: size limits, fuzzing, strict DER and X.509 validation.
- Key theft: HSM/PKCS#11 isolation, no key export by default, no secret logging.
- Serial duplication: unique issuer+serial constraint, durable reservation.
- Signature ambiguity: reconciliation and no blind retry.
- CRL manipulation/staleness: signed CRLs, controlled publication, freshness monitoring.
- Supply chain: pinned dependencies, SBOM, SCA, provenance, signed releases.
- Insider abuse: role separation, privileged action audit, two-person control where justified.

## Revocation and CRL write path (lab, migrations 0014-0032, ADR-0006, ADR-0007)

| An issuance service login stores a certificate that never had a signing intent, rewrites an intent or skips the policy gate | 0035: the issuance functions are SECURITY DEFINER owned by NOLOGIN `trust_issuance_owner` (table rights limited to what the functions and gate triggers need; `ca` only `policy_gate_epoch`); `trust_issuance_service` has EXECUTE only, no table access (tests/revocation_privileges.sql, `issuance_service_role_issues_through_functions_only`) | Since 0043 policy administration (`trust_policy_admin`) and reconciliation/evidence (`trust_reconciliation_operator`) are EXECUTE-only capability roles over definer functions too; their actor identities are still asserted by the caller; `PgIssuanceStore::connect_lab_service` / `from_service_client` refuse a superuser, CREATEROLE, BYPASSRLS or owner-member login, but only for services that use them; superusers and the owner bypass |
| One actor plays maker and checker by asserting two identities | Database refuses equal `(issuer, subject)`; officer grants are server-owned | Identities are asserted by the calling service: textual, not key-distinct (known deviation from AGENTS.md). | Fake coverage: rows added to a CRL snapshot or a `STORED` row inserted without signing | No INSERT for services (0023); snapshot and publication guards; store checks digests | Owner/superuser can still insert |
| CRL signed by another CA's key or stored under the wrong CA | 0022 registered issuer certificate per CA; `crl_once` checks the verifier issuer and the signer's SPKI before the intent | Key rollover not modelled; registration needs two CA admins (0024), signed with distinct keys and persons where `signed_admin_required` is set (0037), textual otherwise; DBA bootstrap outside dual control |
| Shadowing through `search_path` or temporary objects | Service functions pin `search_path = pg_catalog, public, pg_temp` (planted temp table test) | Independent review of every SECURITY DEFINER body (dynamic SQL, error leakage) still required |
| A service runs with a superuser or owner-member login and bypasses everything | `connect_lab_service` refuses privileged `session_user` (0024 commit) | Only enforced by the services that use it; deployment evidence required (ADR-0006 acceptance condition 2) |
| A single officer abuses or is tricked into a precautionary hold (ADR-0007 §6) | 0036: opt-in per CA, only under a CPS suspension reference; the officer signs a distinct `PRECAUTIONARY_SUSPEND` claim with an enrolled WebAuthn credential (single-use challenge); only a valid certificate; reversible hold only; fixed deadline, overdue holds alert in housekeeping; audit event and log line per use | 0038 caps open holds per officer and CA (`precautionary_hold_limit`, default 3) and 0047 per CA for all officers together (`precautionary_hold_ca_limit`, default 10, one per-CA lock); several CAs still add up, and the CA cap lets a few holders exhaust the CA's precaution budget, after which only dual control can suspend (availability, not integrity); the deadline does not lift a hold (fail closed); break-glass (0045) only re-enrols admin keys, it is no faster path for holds |
| One CA admin registers an issuer or grants officers alone, or grants themselves officer rights | 0024 `ca_admin_change`: two distinct admins, approval of the exact content digest, no self-grant. 0037 (opt-in, one-way per CA): both admins sign the `trust-platform/ca-admin/v1` claim with enrolled WebAuthn keys, distinct keys and persons; unsigned paths refused; an officer key or person can never be an admin's; evidence re-verifies offline (`reverify_admin_change`) | Admin keys are bootstrapped by the DBA until `signed_admin_required` is set; after that they change only by signed dual control (0040), and losing keys is recovered only by the 0045 break-glass key (below). DBA removal stays open (it only takes signing power away); the database cannot verify ECDSA, so a holder of `trust_ca_admin` could store a forged assertion (exposed by re-verification; a proposal with a forged maker signature cannot be approved through the Rust core); textual where the setting is off; since 0042 rejection is signed too on such CAs; since 0052 a proposal older than `admin_proposal_max_age_hours` (default 7 days) is no longer approved |
| The emergency (break-glass) key is stolen or misused to take over CA administration (ADR-0007 §6, 0045) | Separate WebAuthn key per CA, enrolled and removed by the DBA only, never an officer or admin key; it can only enrol a CA-admin key for an identity already holding `ca_admin_grant`, only on a signed-administration CA with fewer than two active admin keys (under the CA lock); single-use challenge, counter, assertion verified in Rust; every use stored with its signature, audited, and alerted by housekeeping until two other admins (distinct keys and persons) sign a review; offline re-verification | Custody of the key is procedural; since 0046 the custodian is a person who may hold no officer or admin credential on the CA, but person identifiers are caller-supplied (one human under two identifiers is not detected until the IAM decision); since 0048 enrolments in the three credential registries share one advisory lock, so concurrent enrolments cannot both pass the disjointness checks (tested); a holder of `trust_ca_admin` could store a forged break-glass assertion while the CA has fewer than two keys (since 0051 such a use cannot be reviewed, so it stays open and alerted; `audit_signed_evidence` exposes it; the forged key stays enrolled until removed by dual control, but the Rust core refuses its signatures while the use's evidence does not re-verify); the DBA, who removes the lost keys, is trusted as before; no rate limit beyond the two-key condition |
| Stale or superseded CRL signed late, or a CRL misdated by a wrong database clock | Only the highest reserved number may record an intent; staleness and nextUpdate checks (0017, 0020, 0021); the Rust core refuses a reservation whose thisUpdate disagrees with its clock beyond 2 s and housekeeping alerts on skew (ADR-0006 G) | Both clocks wrong together is not detected; authenticated time (NTS) is a deployment requirement |
| A function, grant or guard is changed outside a reviewed migration (e.g. `SECURITY DEFINER` reset, trigger disabled) | Catalog invariant in tests/revocation_privileges.sql (0025); 0026 event triggers record every DDL and object grant (append-only, `ENABLE ALWAYS`, no SQL text) and `crl_housekeeping` alerts on changes no reviewed migration acknowledged | Role changes are detected since 0057 (reviewed role-state snapshot, `unreviewed_role_changes` alerted by housekeeping) but not prevented or attributed; `ALTER SYSTEM` and event triggers themselves are not recorded (server logging/pgaudit needed); a superuser can drop the triggers or the rows (external anchoring, ADR-0006 condition 5) |
| A superuser rewrites, deletes or truncates the audit trail, or recomputes it consistently | 0027 sealed hash chain over `audit_event` and `schema_change_audit`; Rust re-encodes every record and checks heads against checkpoints exported outside the database (`audit_chain_anchor`, exit 3) | Unsealed records and entries after the last checkpoint; checkpoints signed with a lab key file (HSM custody open) but not third-party timestamped; forged records inserted before sealing are sealed too |
| A CRL altered or substituted in the database is published to relying parties; the public endpoint becomes a write path | 0030: `trust_crl_publisher` can only read the latest stored CRL; the distribution point refuses privileged logins and re-verifies signature, issuer, number and times before serving (503 otherwise); only a verified copy is reused, for 30 s by default, to absorb request floods | No HTTP TLS or availability engineering; a newly stored or altered CRL is reflected up to the reuse window (default 30 s) later (the database link uses verified TLS 1.3); a stale CRL is still served (uncached); denial of service by withholding new CRLs is not detected here (housekeeping `crl_due`) |
| A delta CRL is taken for the complete CRL, so a certificate revoked only in the base looks valid | 0059: `published_crl` and the CDP serve complete CRLs only; deltas only at `/delta`, re-checked with `verify_published_delta_crl` (critical indicator, base below the number); `verify_published_crl` refuses any delta or critical extension; publication deadlines count complete CRLs only | A relying party that loads base and delta into OpenSSL without `-extended_crl` treats the newer delta as complete (observed with OpenSSL 3.0); delta issuance is on demand, not scheduled |
| A restore from an older backup silently un-revokes certificates revoked since | 0060: `crl_restore_revocations` re-applies the last published CRL's entries after verifying it against the registered issuer; superuser only; never releases a hold or changes a definitive revocation; evidence kept, audited, CRL number floor raised | Certificates issued after the backup are lost with their revocation (reported `UNKNOWN_CERTIFICATE`, handled by hand); changes after that CRL are lost; not rehearsed against an actual older `pg_restore` |
| A revoked certificate silently disappears from CRLs through pruning | 0031: pruning is opt-in, refused for ETSI EN 319 411-2, only after a stored CRL issued past `not_after` listed the entry; `not_after` comes from the verified certificate at issuance and is immutable; NULL is never pruned | Since 0032 the Rust core re-reads every omitted entry's stored certificate before signing and refuses an expiry the DER does not confirm. Residual: a superuser can replace the stored DER and `not_after` together (since 0035 the issuance service login cannot) |
| An HTTP caller acts as another officer, or a service answers a challenge on an officer's behalf | Revocation write API (lab): actor = verified token `(iss, sub)`, role and CA scope required, unknown fields refused, challenge bound to its officer, assertion verified in Rust before writing, officer-API login only | Per-identity budget of 60 requests per minute (429), per process and in memory, so replicas or restarts reset it; TLS 1.3 on the HTTP side only when a certificate is configured (plain HTTP is refused off loopback unless the logged lab opt-out is set), no mTLS or session binding beyond the token (database connections use verified TLS 1.3 since iteration 19); a holder of the officer API database role can still bypass the API (ADR-0007 §7); a proposal it stores with a forged maker signature cannot be approved through the Rust core, which re-verifies the maker's evidence first |
| An authenticated officer or admin (or a stolen token) floods the database with signing challenges | 0049: at most 16 unexpired, unconsumed challenges per actor, CA and kind (status change, CA administration), checked under a per-actor lock; expired and consumed challenges stop counting; the HTTP APIs also bound concurrent requests | Consumed challenges are evidence and kept; since 0053 housekeeping purges challenges that expired unused more than 30 days ago (audited), so the table grows with consumed challenges and a 30-day window of unused ones; the HTTP APIs add a per-identity budget (60 requests per minute), but no per-IP limit |
| Lost or ambiguous signature | Durable intent before signing, quarantine, reconciliation of a held DER (0021), housekeeping alerts | A CRL lost with its process cannot be recovered (no signer read-back) |
