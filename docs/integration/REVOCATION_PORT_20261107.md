# Revocation port checkpoint — updated 2026-11-08

This branch ports the experimental Claude PR #94 onto the profile-lifecycle integration branch. It is an **incomplete laboratory integration** and must not be merged into `main` or deployed yet.

## Applied work and evidence

- The profile stack keeps migrations `0014`–`0025`. All 52 migrations from #94 were moved in their original order to `0026`–`0077`; their exact migration references inside SQL were changed with their filenames. A new `0078` bridge makes verified profile issuance populate the expiry used by CRL pruning and grants the internal issuance function owner the rights needed by the SAN synchronization trigger. A disposable PostgreSQL 16 database accepted the full `0001`–`0078` sequence.
- On that database, the SQL suites `revocation_lifecycle`, `crl_pipeline`, `crl_robustness`, `ca_admin_dual_control`, `signed_status_changes`, `audit_chain`, and `crl_delta` passed. On a populated upgrade database, the `revocation_privileges`, `crl_entries_digest` and `status_change_audit_decision` suites also passed.
- `scripts/lab/migrate.sh` now accepts an existing profile database through `0025` only with `--adopt` and an exact matching `management_migration_ledger`. A disposable `0025` database upgraded through the ported migrations, a second run applied nothing, and a modified migration file was refused. A second upgrade with two synthetic CAs, a certificate and an audit event retained all rows and certificate bytes; the digest ledger recorded the applied files. This test used a generated 14-entry profile ledger. An existing lab database without that ledger is intentionally refused. The full `revocation_migration_runner.sh` suite passed again through `0078`: fresh migration, adoption, checksum drift, missing file, lock contention, future/gapped history, privilege refusal and transactional failure. `revocation_populated_upgrade.sh` passed through `0078` with legacy revocations after applying the profile migrations before the ported revocation sequence.
- The new CA administration and revocation APIs require the same explicit OIDC client binding as the profile API. Their test-token helpers now include the client and issue time claims. `cargo check --workspace --all-targets --all-features --locked` and `cargo test --workspace --all-targets --all-features --locked` passed in the pinned Rust 1.99.0 container after dependency alignment. With a disposable PostgreSQL database, all 22 `revocation_crl_postgres`, 31 `signed_status_change_postgres` and three `audit_chain_postgres` tests passed. The CA administration and revocation API binaries also passed all 39 and 40 tests respectively with their database URL set, executed serially because concurrent tests create the same fixed CI role. The full workspace run itself had no database test URLs.
- The original profile management API `main.rs` was retained. Automatic text merging produced an incoherent hybrid of profile and #94 handlers. The shared HTTP/TLS transport, connection limits, no-store/nosniff response headers, per-client and per-identity request limits, database TLS and an idle read-connection cache have since been integrated explicitly. The writer login uses the same database TLS policy but retains no idle connection. A PostgreSQL test verified that a reused reader session discards the previous principal and reapplies its statement timeout; the management API binary tests pass. The separately added revocation and CA administration binaries compile.
- The Compose database initialization now generates and provisions distinct housekeeping, auditor, sealer, revocation API and CA-administration API credentials in addition to the existing profile logins. A fresh isolated seven-service Compose stack applied all 78 migrations, seeded the profile fixtures and started the database, Keycloak, management API, frontend, scheduled jobs and both control APIs, all healthy. The first job round completed CRL housekeeping, audit sealing, checkpoint verification and signed-evidence audit with exit status zero. Both control APIs answered 401 without a token; database checks confirmed that their capability roles are distinct and neither login has direct access to its sensitive tables. The CI Compose workflow now repeats these checks. The existing Keycloak code/PKCE smoke scenario passed against the rebuilt management API: a real reader signed in, read only its granted CA and was refused access to the other CA. The run exposed and corrected a Unicode length mismatch in the `policy_version` filter. This does not exercise a signed OIDC/WebAuthn status change or CA-administration journey.
- Docker's build context now excludes `.lab-keys` as well as `.env.lab`. A test build copied the entire filtered context and confirmed that neither private laboratory key files nor the credential file were present. The seven services were rebuilt from that context and returned healthy.
