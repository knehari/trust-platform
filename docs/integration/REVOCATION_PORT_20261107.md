# Revocation port checkpoint — updated 2026-11-08

This branch ports the experimental Claude PR #94 onto the profile-lifecycle integration branch. It is an **incomplete laboratory integration** and must not be merged into `main` or deployed yet.

## Applied work and evidence

- The profile stack keeps migrations `0014`–`0025`. All 52 migrations from #94 were moved in their original order to `0026`–`0077`; their exact migration references inside SQL were changed with their filenames. A disposable PostgreSQL 16 database accepted the full `0001`–`0077` sequence.
- On that database, the SQL suites `revocation_lifecycle`, `crl_pipeline`, `crl_robustness`, `ca_admin_dual_control`, `signed_status_changes`, `audit_chain`, and `crl_delta` passed. On a populated upgrade database, the `revocation_privileges`, `crl_entries_digest` and `status_change_audit_decision` suites also passed.
- `scripts/lab/migrate.sh` now accepts an existing profile database through `0025` only with `--adopt` and an exact matching `management_migration_ledger`. A disposable `0025` database upgraded through all 52 ported migrations, a second run applied nothing, and a modified migration file was refused. A second upgrade with two synthetic CAs, a certificate and an audit event retained all rows and certificate bytes; the digest ledger recorded 77 files. This test used a generated 14-entry profile ledger. An existing lab database without that ledger is intentionally refused. The full `revocation_migration_runner.sh` suite also passed: fresh migration, adoption, checksum drift, missing file, lock contention, future/gapped history, privilege refusal and transactional failure. `revocation_populated_upgrade.sh` passed with legacy revocations after applying the profile migrations before the ported revocation sequence.
- The new CA administration and revocation APIs require the same explicit OIDC client binding as the profile API. Their test-token helpers now include the client and issue time claims. `cargo check --workspace --all-targets --all-features --locked`, both API binaries' targeted tests (39 and 40 passing), and `cargo test --workspace --all-targets --all-features --locked` passed in the pinned Rust 1.99.0 container after dependency alignment. The full workspace run does not establish database-backed coverage for tests that skip when no test URL is provided.
- The original profile management API `main.rs` was retained. Automatic text merging produced an incoherent hybrid of profile and #94 handlers, so #94's management API rate-limit, TLS, database and response-header additions are **not integrated** into that binary. The separately added revocation and CA administration binaries compile.
- The Compose database initialization now generates and provisions distinct housekeeping, auditor and sealer credentials in addition to the existing profile logins. An isolated Compose PostgreSQL service applied all 77 migrations, seeded the profile fixtures, created five restricted logins and accepted all three job-login credentials. Explicit digest adoption recorded 77 files. The isolated Compose project and generated laboratory credentials were removed after the test; the jobs image and full multi-service stack were not run.

The database initialization has been tested in isolation, but the textual merge has not been accepted as full semantic integration. 2. Run database-backed API and core tests, frontend and Compose suites, logical restore, CRL/revocation fault paths and final-head CI. The full Rust workspace suite and SQL migration suites pass, but the Rust run had no database test URLs and is not end-to-end proof. The main management API still lacks the #94 transport/rate-limit additions, which need an explicit design integration.
4. Link the G0 legal/IP and independent security-review artifacts. The user confirmed both decisions are complete, but their evidence is not yet in this repository checkpoint.

No production keys, authorities or data were used. The disposable migration test databases and container test copies were removed after the checks.
