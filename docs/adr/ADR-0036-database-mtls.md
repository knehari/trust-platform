# ADR-0036 — Mutual TLS between the services and PostgreSQL

**Status:** Proposed · 2026-11-11. It is not accepted; acceptance needs the
owner's decision and an independent security review (AGENTS.md). It is the
mTLS part of the review's P0 item "TLS and mTLS everywhere", after
ADR-0031 to ADR-0033.

**Scope:**
- `trust-db-connect` and `trust-db-check`;
- the laboratory database's client authentication (`pg_hba.conf`, its CA);
- the per-login client certificates generated by `init-env.sh`;
- the compose services `api`, `signer` and `publisher`;
- `tests/database_tls.sh` and CI.

**Out of scope:**
- mTLS between the browser and the API: users authenticate with OIDC;
- the RA channel, which authenticates each request with its signature
  (ADR-0025);
- the API and signer link, a Unix socket that only the API's user can open;
- certificate rotation, revocation of service certificates, and a secret
  store.

## Context

Since ADR-0031, every service connects to PostgreSQL over TLS and verifies
the server certificate. The database still authenticated clients only by
password. A leaked service password (from `.env.lab`, a process
environment or a log) let anyone who could reach the database log in as
that service.

## Decision

1. **Two factors for every network login.** The laboratory `pg_hba.conf`
   accepts network connections only with:
   - `hostssl ... scram-sha-256 clientcert=verify-full`. The client must
     present a certificate from the lab service CA whose common name is the
     login name, and also give the login's password;
   - TLS (plaintext is still rejected).

   Only the local socket inside the database container (initialisation, the
   owner's `psql`) skips both checks.
2. **One certificate per login.** `init-env.sh` issues, from the service CA
   of ADR-0031:
   - `trust_api_lab` and `trust_api_writer_lab`, mounted only into the API;
   - `trust_signer_lab`, mounted only into the signer;
   - `trust_publisher_lab`, mounted only into the publisher.

   Each certificate has the `clientAuth` extended key usage, a P-256 key and
   a 90-day lifetime. A service cannot present another service's
   certificate, and the database refuses a certificate whose name is not
   the login's.

   PostgreSQL does not allow a user-name map with SCRAM, so the API's two
   logins need two certificates.
3. **The connector picks the login's certificate.** With
   `TRUST_DATABASE_CLIENT_CERT_DIR`, `trust-db-connect` presents, on every
   connection, `<dir>/<user>.crt` and `<dir>/<user>.key` for the URL's
   user. The following are errors:
   - a missing file;
   - a key that does not match the certificate;
   - a login name that is not a plain identifier (so it cannot name a path);
   - the variable set without `TRUST_DATABASE_CA_FILE`.

   The connector never connects without the certificate.
4. **Visibility.**
   - The API logs `database_client_cert` at startup.
   - `trust-db-check` prints the client certificate subject that the server
     saw (`pg_stat_ssl.client_dn`).
   - Server error messages, for example "connection requires a valid client
     certificate", now appear in the connector's errors.

## Alternatives considered

- **`cert` authentication without a password.** It allows a user-name map,
  so one certificate could serve the API's two logins. Rejected: the
  certificate alone would then be enough, and a leaked key file would
  replace the password instead of adding to it.
- **`clientcert=verify-ca`.** It accepts any certificate from the CA for any
  login, so any service could present its own certificate as another
  login. `verify-full` binds the certificate to the login.

## Consequences and open risks

- **Same CA for servers and clients.** One lab service CA signs the
  database, API and Keycloak server certificates and the client
  certificates. A client certificate cannot impersonate a server: names
  and extended key usage differ, and clients check the server name.
  Splitting the CAs remains an option.
- **The API's client keys are world-readable** (mode 0644): the API runs as
  `nobody` and reads a bind mount, as for its HTTPS key (ADR-0032). They are
  protected by the host's 0700 `.lab-keys/tls/clients/` directory. The
  signer's and publisher's keys are 0600.
- **No rotation or revocation.** The certificates last 90 days, and
  `init-env.sh` issues new ones only when they are missing. The server does
  not check a CRL for client certificates.
- **Existing stacks.** A stack started before this change needs
  `init-env.sh` to be run again, which issues the client certificates, and
  a restart of the database with its new CA option.

## Tests

- `tests/database_tls.sh`, in the Rust CI job, on a throwaway cluster:
  - accepted: the login's certificate with the right password; the server
    sees `/CN=<login>`;
  - refused:
    - no certificate (by the server);
    - no certificate for the login in the directory (by the client);
    - another login's certificate;
    - a certificate from another CA;
    - a key that does not match its certificate;
    - a wrong password, even with the right certificate;
    - a certificate directory without a CA file.

  The script also now stops its cluster when it runs as root.
- `trust-db-connect` unit tests: refusal of path-like or empty login names
  and of missing files.
- CI's compose job:
  - plaintext is refused;
  - TLS with the API's password but no certificate is refused with
    "connection requires a valid client certificate";
  - every `hostssl` rule the server loaded requires `verify-full`, and there
    is no plain `host` rule;
  - the services pass every suite through that listener.
- Locally, against a cluster that requires certificates for the four service
  logins:
  - all e2e suites passed;
  - `trust-db-check` showed `/CN=trust_api_writer_lab`;
  - the signer's login was refused both with the API's certificates and
    without a certificate.
