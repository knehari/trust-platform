# ADR-0031 — TLS with server verification for every PostgreSQL connection

**Status:** Proposed · 2026-11-11. It is not accepted; acceptance needs the
owner's decision and an independent security review (AGENTS.md). It is the
first slice of the review's P0 item "TLS and mTLS everywhere", chosen by
the owner on 2026-11-11.

**Scope:**
- the new crate `trust-db-connect`;
- the API, the lab signer, the CRL publisher, the audit tools and the
  migration runner;
- the laboratory TLS PKI generated by `init-env.sh`;
- the compose database configuration;
- CI.

**Out of scope:**
- HTTPS for the API and Keycloak, a later slice;
- mTLS client certificates;
- secrets management.

## Context

Every process connected to PostgreSQL in plaintext (`NoTls`). On the
laboratory network, and on any real deployment, the following travelled
unencrypted:
- passwords (SCRAM limits exposure, but the session is not protected);
- every query;
- CSRs, certificates, decisions and audit events.

An active attacker on that network could alter results. For example, it
could feed the signer a forged intent view or the publisher a forged CRL.
The signer's and publisher's own checks would catch many such forgeries,
but not all.

## Decision

1. **One connector.** All production connections go through
   `trust_db_connect::connect` (or `connect_config` in the API's pool path).
2. **TLS is required when configured.** When `TRUST_DATABASE_CA_FILE` names
   a PEM file:
   - `sslmode=require` is forced, so a server without TLS is refused;
   - a URL asking for `sslmode=disable` is refused;
   - a missing or invalid CA file is an error, never a plaintext fallback.
3. **The server is verified.** rustls (the ring provider, already locked
   through `reqwest`) checks the server certificate chain against the
   configured file only, never the system roots. It also checks the
   certificate's name against the URL host, including IP SANs.
   TLS 1.2 is the minimum.
4. **Laboratory PKI.** `init-env.sh` generates, in the ignored
   `.lab-keys/tls/`:
   - a P-256 service CA;
   - a server certificate for `db`, `localhost` and `127.0.0.1`.

   The CA key is mounted in no container. Only `db.crt` and `db.key` reach
   the database, copied with the ownership and mode PostgreSQL requires.
   Only `ca.crt` reaches the clients.
5. **The laboratory database refuses plaintext TCP.**
   - `scripts/lab/pg_hba.conf` allows the local socket (initialisation
     scripts, the owner's psql inside the container) and `hostssl` with
     SCRAM;
   - it rejects `hostnossl`.
6. **Visibility.** The API logs `database_tls` at startup.
   `trust-db-check <url> [--require-tls]` reports whether a connection is
   encrypted and with which protocol.

## Alternatives considered

- **OpenSSL bindings** (`postgres-openssl`): a system dependency in every
  image. rustls is already in the lockfile.
- **Trusting the system roots:** any public CA could then impersonate the
  database. Only the platform's own service CA is trusted.
- **Requiring TLS unconditionally:** CI's loopback test databases and the
  test helpers stay plaintext. The policy is explicit per process, and the
  laboratory and any deployment set it.

## Consequences and open risks

- **Plaintext by default.** Without `TRUST_DATABASE_CA_FILE` a process
  still connects in plaintext. A deployment must set it, and the API's
  startup log shows whether it did.
- **No client certificates (mTLS) yet.** Authentication stays
  SCRAM passwords over TLS.
- **Lab certificate lifetime.** The lab server certificate is valid 90
  days and the CA 1 year. `init-env.sh` regenerates them only when they
  are missing; there is no rotation tooling.
- **Expected plaintext uses.** Test helpers and CI's database tests keep
  `NoTls`. The legacy `pki-core` PostgreSQL store also does, and it is
  test-only.

## Tests

- `tests/database_tls.sh`. It runs a throwaway cluster that accepts only
  TLS, with a throwaway CA, and checks `trust-db-check` against it:
  - verified TLS by IP and by name;
  - another CA refused;
  - `sslmode=disable` refused by the client;
  - plaintext refused by the server;
  - a certificate for another name refused;
  - a missing CA file refused.

  It runs in the Rust CI job.
- `trust-db-connect` unit tests: invalid CA files, and no plaintext
  fallback.
- The laboratory compose job. After the suites ran over the TLS-only
  listener, the database refuses a plaintext TCP connection and serves a
  TLS one.
- Locally, the API, signer and publisher ran the e2e suites with the
  policy set against a TLS-enabled cluster.
