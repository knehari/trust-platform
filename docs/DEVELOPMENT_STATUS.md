## This increment

Migration 0021 filters each of seven management views by the principal declared on the PostgreSQL session. The API already denied reads without token scope and grants, but its startup/readiness gate checked only `management_ca` and `management_reader_scope`. A later unfiltered certificate, audit, SAN, history-bound or profile view could therefore pass the gate. The gate now checks all seven views for zero rows on a session without a principal. It still checks the migration marker. API request authorization is unchanged.

A restricted PostgreSQL login on a disposable database with migrations 0001–0021 ran `reader_isolation_gate_checks_every_management_view`. The test temporarily shadowed each view with a one-row unfiltered view. It **failed before the fix** on `management_certificate` and **passed after the fix** for all seven views. The full API suite also passed **22/22** without database variables (its database-dependent cases skipped); the targeted isolation test above exercised the disposable database. `cargo fmt --all -- --check`, `cargo clippy -p trust-management-api --all-targets --locked -- -D warnings` and `git diff --check` passed. On a disposable database with 100,000 synthetic audit events, one `EXPLAIN ANALYZE` run of the new no-principal gate took 2.55 ms planning and 0.17 ms execution; the previous two-view gate took 0.65 ms and 0.05 ms on the same fixture. PostgreSQL never scanned the audit table because the grant lookup returned no principal. This is one local sample, not a latency guarantee. The frontend suite and a broader load measurement remain open before a PR. No application database or GitHub branch was changed by the test.
