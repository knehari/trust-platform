# Read-only management API laboratory increment

This increment is a **running service**, but it is not a deployed application, a CA issuer or a production authentication integration. It implements the first read-only boundary from [ADR-0005](../adr/ADR-0005-rust-management-control-plane.md). The Rust CA Core remains in the workspace and is not invoked by these metadata reads. Issuance remains reachable only through existing laboratory harnesses, not HTTP.

## Contract and trust boundary

The [OpenAPI v1 contract](../../openapi/management-v1.yaml) describes health, CA list/detail, certificate metadata and audit metadata. All data endpoints require a signed RS256 OIDC access token with `typ=at+jwt`, exact issuer/audience, `exp`, `nbf`, `sub`, the `trust-ca-reader` role and explicit canonical UUIDs in `ca_ids`. No wildcard or caller-supplied scope is supported. OIDC discovery and JWKS are fetched at service startup; the issuer must use HTTPS, except localhost HTTP for a laboratory provider. JWKS must share the issuer origin and use distinct RSA signing `kid`s. Unknown/rotated keys fail closed until restart. The service does not accept ID tokens, HMAC JWTs or arbitrary identity headers.

The server filters each query by the intersection of signed CA scope and server-managed issuer/subject/CA grants. Migration `0013_management_reader_grants.sql` adds a grant table and a limited projection readable by the `trust_api_reader` role; this role cannot read or write the source table. No grant means no access, including when a correctly signed token names the CA. The issuer is part of the grant key, so identical subjects from different issuers do not share access. Migration 0012 still confines certificate and audit reads to limited views. Queries are parameterized and responses are bounded to 100 rows. Deployment must create a separate login and grant `trust_api_reader` to it. Startup verifies role isolation and grant-view availability. The SQL fixture proves the role cannot read raw grants or certificate DER, update CAs or execute the issuance function. It does **not** replace a full database privilege audit, tenant isolation review or signed audit export.

At most eight database requests may run concurrently in this laboratory service. Requests above the bound fail promptly with HTTP 503 before scheduling blocking work; the permit is held through connection and query completion. PostgreSQL connection establishment has a three-second timeout. This reserves a finite application-side budget but is not a deployment capacity plan, rate limit or substitute for a dedicated production connection pool.

The service writes one JSON line per completed HTTP request with a generated `X-Request-Id`, method, status, elapsed milliseconds and timestamp. The same ID is returned in the response header. It deliberately omits Authorization headers, raw URLs/query strings, request/response bodies and database errors. These process logs are diagnostic only: they are neither durable PKI audit events nor independently signed evidence. Central log handling, retention and security-event design remain open.

## Run in a disposable lab

Apply migrations `0001`–`0013` in order to a disposable PostgreSQL 16 database. As database owner, provision exact issuer/subject/CA reader grants; the API exposes no grant-write endpoint. Create a separate login, grant `trust_api_reader`, and set `TRUST_DATABASE_URL` to that login's connection URL. Set `TRUST_OIDC_ISSUER` to an HTTPS issuer (or localhost HTTP for a test issuer), `TRUST_OIDC_AUDIENCE` to the API audience, and optionally `TRUST_API_BIND` (default `127.0.0.1:8081`). Run `cargo run -p trust-management-api --locked`. The API fails startup if discovery, JWKS, grant projection or role isolation fails. `GET /v1/health` exposes only `{"status":"up"}`; it is liveness, not database readiness.

The configured PostgreSQL driver uses `NoTls`, so this build is for a local/disposable lab only. A future deployment requires authenticated database transport, secret management, a production connection pool and capacity limits, JWKS refresh, durable security-event logging, rate limiting and operational readiness. The role claim mapping is deliberately narrow. The dependent [React console](../../frontend/README.md) adds a laboratory frontend and a loopback-only auto-approved OIDC fixture; that fixture is not real human authentication. Policy-controlled issuance and HSM integration remain open.

## Evidence and remaining gates

Unit/HTTP tests generate ephemeral RSA keys and validate positive signature, audience, expiry, token type, tampering, missing role and out-of-scope CA rejection. With `TRUST_API_TEST_DATABASE_URL` set to the restricted login, the HTTP test reads one provisioned CA from a populated two-CA database while rejecting an unprovisioned subject and a grant held only under another issuer. The capacity test verifies prompt rejection while the only slot is held, then successful access after release. The database CI job applies migration 0013, runs its privilege fixture and reruns these tests. Without this variable, the tests do not claim database coverage. G0 and independent security review remain open.
