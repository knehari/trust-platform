# Read-only management API laboratory increment

This increment is a **running service**, but it is not a deployed application, a CA issuer or a production authentication integration. It implements the first read-only boundary from [ADR-0005](../adr/ADR-0005-rust-management-control-plane.md). The Rust CA Core remains in the workspace and is not invoked by these metadata reads. Issuance remains reachable only through existing laboratory harnesses, not HTTP.

## Contract and trust boundary

Every HTTP response, including successful reads and authentication or capacity failures, carries `Cache-Control: no-store` so clients are instructed not to retain management metadata or access decisions. This header does not replace TLS or control copies made outside HTTP caches.

The [OpenAPI v1 contract](../../openapi/management-v1.yaml) describes liveness, readiness, CA list/detail, paged certificate metadata and a request-ID certificate detail, and paged audit metadata with an event-ID detail. All data endpoints require a signed RS256 OIDC access token with `typ=at+jwt`, exact issuer/audience, `exp`, `nbf`, `sub`, the `trust-ca-reader` role and explicit canonical UUIDs in `ca_ids`. No wildcard or caller-supplied scope is supported. OIDC discovery and JWKS are fetched at service startup; the issuer must use HTTPS, except localhost HTTP for a laboratory provider. JWKS must share the issuer origin and use distinct RSA signing `kid`s. The verifier refreshes an unknown key ID on demand, at most once every five seconds, and refreshes any key set older than 60 seconds before accepting a token. A refresh failure or invalid/empty new key set denies tokens once the cache is stale; a successful refresh replaces removed keys rather than retaining them. Therefore removal can take up to 60 seconds to take effect for a previously cached key. The service does not accept ID tokens, HMAC JWTs or arbitrary identity headers.

The server filters each query by the intersection of signed CA scope and server-managed issuer/subject/CA grants. Migration `0013_management_reader_grants.sql` adds a grant table and a limited projection readable by the `trust_api_reader` role; this role cannot read or write the source table. No grant means no access, including when a correctly signed token names the CA. The issuer is part of the grant key, so identical subjects from different issuers do not share access. Migration 0012 confines certificate and audit reads to limited views. Migration 0014 adds a nullable subject CN to the restricted certificate projection; the Rust laboratory journal records it only after certificate verification, and historical rows remain null. Queries are parameterized. CA, certificate and audit responses contain at most 100 rows per page; the optional `X-Next-Cursor` header carries the next position. CA ordering uses display name plus CA ID, while certificate and audit ordering uses timestamp plus unique record ID to avoid losing rows with equal timestamps. The server rechecks signed scope and database grants on every page. This is a bounded laboratory browser, not a snapshot across concurrent writes or a production query-performance guarantee. Deployment must create a separate login and grant `trust_api_reader` to it. Startup verifies role isolation and grant-view availability. The SQL fixture proves the role cannot read raw grants or certificate DER, update CAs or execute the issuance function. It does **not** replace a full database privilege audit, tenant isolation review or signed audit export.

At most eight database requests may run concurrently in this laboratory service. Requests above the bound fail promptly with HTTP 503 before scheduling blocking work; the permit is held through connection and query completion. PostgreSQL connection establishment and each SQL statement have separate three-second timeouts. A timed-out query returns HTTP 503 without exposing a database error, and its connection and permit are released. This reserves a finite application-side budget but is not a deployment capacity plan, rate limit or substitute for a dedicated production connection pool.

The service writes one JSON line per completed HTTP request with a generated `X-Request-Id`, method, status, elapsed milliseconds and timestamp. The same ID is returned in the response header. It deliberately omits Authorization headers, raw URLs/query strings, request/response bodies and database errors. These process logs are diagnostic only: they are neither durable PKI audit events nor independently signed evidence. Central log handling, retention and security-event design remain open.

## Run in a disposable lab

Apply migrations `0001`–`0016` in order to a disposable PostgreSQL 16 database. As database owner, provision exact issuer/subject/CA reader grants; the API exposes no grant-write endpoint. Create a separate login, grant `trust_api_reader`, and set `TRUST_DATABASE_URL` to that login's connection URL. Set `TRUST_OIDC_ISSUER` to an HTTPS issuer (or localhost HTTP for a test issuer), `TRUST_OIDC_AUDIENCE` to the API audience, and optionally `TRUST_API_BIND` (default `127.0.0.1:8081`). Run `cargo run -p trust-management-api --locked`. The API fails startup if discovery, JWKS, grant projection or role isolation fails. `GET /v1/health` exposes only `{"status":"up"}` for process liveness. Unauthenticated `GET /v1/ready` returns `{"status":"ready"}` only when an authenticated-read request slot is free, the restricted PostgreSQL login and all five management views are available; otherwise it returns a generic 503 without database details. Probes use one separate database slot and a one-second result cache, so anonymous callers cannot occupy the eight slots reserved for reads; concurrent probes fail promptly. Compose uses readiness to gate the frontend. Neither endpoint validates production IAM or CA signing capability.

The data routes share a 16-request, fail-fast HTTP concurrency budget. A permit is acquired before token parsing or a possible JWKS refresh and held until the database read completes; excess data requests return 503 with a request ID. Liveness and readiness have separate paths, so data-route saturation does not consume their HTTP budget. This is a process-local concurrency bound, not per-client rate limiting or a measured production capacity setting. The configured PostgreSQL driver uses `NoTls`, so this build is for a local/disposable lab only. A future deployment requires authenticated database transport, secret management, a production connection pool and capacity planning, durable security-event logging, request rate limiting and operational readiness. The role claim mapping is deliberately narrow. The dependent [React console](../../frontend/README.md) adds a laboratory frontend and a loopback-only auto-approved OIDC fixture; that fixture is not real human authentication. Policy-controlled issuance and HSM integration remain open.

## Evidence and remaining gates

Unit/HTTP tests generate ephemeral RSA keys and validate positive signature, audience, expiry, token type, tampering, missing role and out-of-scope CA rejection. With `TRUST_API_TEST_DATABASE_URL` set to the restricted login, the HTTP test reads one provisioned CA from a populated two-CA database while rejecting an unprovisioned subject and a grant held only under another issuer. The HTTP capacity contract exhausts all 16 data permits, confirms every data route immediately returns 503 with a request ID, confirms liveness remains 200 and verifies no database permit was consumed. The readiness contract verifies 200 for an available restricted database, generic 503 for an unreachable database, exhausted database request slots or concurrent probes, preservation of all eight authenticated-read slots, and recovery after releasing slots. The database capacity tests verify cancellation of a five-second SQL sleep by the three-second statement timeout and successful access afterward. The database CI job applies migrations through 0016, runs its privilege fixture and reruns these tests. Without this variable, the tests do not claim database coverage. G0 and independent security review remain open.

## Scoped history queries (laboratory extension)

Certificate pages accept an optional literal, case-insensitive `cn` prefix (2–255 characters), exact, case-insensitive ASCII `san_dns` (1–253 characters), and `not_after_before` (exclusive UTC timestamp) for recorded X.509 validity end dates. These filters can be combined and must be retained on each cursor page. Wildcards in CN are escaped; historical null CNs, SANs or validity dates do not match their respective filters. The validity cutoff compares recorded metadata only and is not a trust or revocation decision. Every page retains the signed CA scope and current database reader grant. Audit pages accept optional `from` (inclusive UTC), `until` (exclusive UTC), exact `event_type`, exact `decision` and exact `policy_version` filters. The same filters must be sent with each cursor; results remain capped at 100 rows and are not a transactionally consistent snapshot. These filtered queries retain the three-second SQL timeout but have not yet been shown to use an index through the security-barrier management views. They need query-plan and load evidence before large-history use.

CA inventory pages also accept a literal case-insensitive `q` prefix over display name or policy version. The query is applied only after signed CA scope and server-owned grant intersection, and must accompany every subsequent cursor. The view remains bounded to 100 rows per page; query-plan and large-scope performance evidence remain open.

Certificate and audit pages support `order=newest|oldest` over the complete scoped history. Cursor comparison changes with direction, while timestamp plus unique ID remains the stable tie-breaker. The console labels CN, serial, event-type and decision sorts as loaded-row operations; those are not server-wide sorts.

New verified lab issuance records expose certificate validity and DNS subject alternative names extracted from the signed DER after independent verification. Historical rows retain null values; the console does not infer these fields from request or CSR data. The console labels whether the current time is inside the recorded period. This is only a comparison of stored dates, not path validation, revocation checking or a trust decision. The management view remains security-barrier protected and returns metadata only, never certificate DER or private keys. The Compose browser fixture assigns synthetic SAN/validity metadata to one invalid-DER sentinel solely to test read-only search; it is not issuance evidence.

The console can export up to 100 explicitly checked, currently visible certificate or audit rows as CSV. Export uses the same allowlisted metadata as the read-only API; it does not fetch extra records or export raw DER, keys, actor identifiers or evidence. The client quotes cells and prefixes spreadsheet-formula-looking values with an apostrophe. Selection is cleared when the session, authority or server query changes.

## Inert profile-draft reads

Migration 0016 adds immutable, versioned proposal rows; every row remains DRAFT and none authorizes issuance. `GET /v1/cas/{ca_id}/profile-drafts` returns at most 100 revisions per page after checking both signed CA scope and the current server-owned reader grant. The cursor orders by profile ID and revision. Only the limited management view is granted to the API reader; the source table and its writes remain inaccessible. A separate approval and key-custody control plane is required before profiles can become active.

The list accepts an optional exact `profile_id` to retrieve all recorded revisions of one proposal within the authorized CA, including revisions beyond the initial unfiltered page. Keep the filter on each cursor page; malformed IDs or a cursor for another profile return 400. A filtered empty list does not reveal proposals in another CA.

For one filtered profile, `order=oldest|newest` controls revision order. Oldest is the default; newest requires `profile_id` and puts the highest revision first. The selected order and profile filter must accompany every cursor page. This sorts immutable revision numbers, not recording timestamps, and does not imply that any draft is effective policy.

The API reports `proposal_warnings` for blank display/policy labels, malformed or repeated proposed DNS zones, and malformed or repeated signature-suite identifiers. These are advisory shape checks on stored drafts. An empty list does not validate DNS ownership, cryptographic support, certificate policy, provider custody or approval.

The `snapshot_sha256` field is SHA-256 over a domain-separated `trust-platform/profile-draft/v1` envelope: CA ID, profile ID, revision, display name, policy version, maximum validity and SAN count, then the ordered DNS-zone and signature-suite arrays. Strings and array counts use eight-byte big-endian length prefixes; integer fields use four-byte big-endian encoding. Creator and recording time are provenance and are excluded. The hash identifies the exact proposed policy content but is neither a signature nor an approval receipt. Any future activation must bind independently authenticated approval evidence to this digest and re-read the immutable source revision.

`GET /v1/cas/{ca_id}/profile-drafts/{profile_id}/{revision}` reads one exact revision after rechecking both signed CA scope and current server-owned grant. It returns 400 for malformed identifiers, 403 for denied scope/grant and 404 only for a missing revision within an authorized CA; it cannot retrieve raw source-table fields or turn a proposal into an active profile.

The console can compare two exact revisions fetched through this route even when they are absent from the loaded list page. Selection is held only in memory and cleared when CA, session, list filter or sort changes; the comparison requires matching CA and profile IDs, different revision numbers and DRAFT status. It does not fetch or infer an active policy.

A comparison link carries only the selected CA UUID, profile ID and two canonical revision numbers. Opening it after sign-in performs two fresh scoped detail reads; malformed or duplicate revision parameters are rejected before routing. The link contains no credential, digest approval or cached proposal content.

The console validates each proposal response before use: exact CA and optional requested revision, canonical profile ID, DRAFT status, bounded numeric fields and arrays, timestamp and digest syntax. It constructs an allowlisted client object, dropping unexpected response properties. This detects malformed API data and prevents accidental display or export of extra fields; it does not prove that the API or stored proposal is authentic or approved.
